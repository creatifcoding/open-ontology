Open Ontology · Configuration as code for every platform

Configuration for every platform, checked as one program.

Salesforce objects, Stripe prices, Okta groups, and GitHub teams already depend on one another. Today those dependencies are implicit: copied by hand between dashboards, and verified by no one.

Open Ontology describes each platform with a Forma prelude that elaborates to its native configuration. Preludes share a standard library of domain types, so every reference between projects is type-checked before anything is deployed.

01The standard library

The ontology is a standard library of domain types.

@ontology/std defines the concepts every business shares: people, organizations, teams, money, and email. It's written in the Palantir-style ontology prelude as interfaces and value types. Platform preludes don't rebuild these. They say which of their own types implement them, so a project can accept “any organization” without caring which platform it came from.

@ontology/std/src/business.formastd
(export Email Currency Money
        Person Organization Team member-of)

(value-type Email String :pattern "^[^@]+@[^@]+$")
(value-type Currency (Enum :usd :eur :gbp :jpy))
(value-type Money {:amount Int :currency Currency})

(interface Person {:name String :email Email})
(interface Organization {:name String :domain (Option String)})
(interface Team {:name String})

(link-type member-of Person Team)
@ontology/salesforce/src/std.formasalesforce
(import "@ontology/std" :as std)

(implements std/Organization Account
  {:name Name :domain Website})
(implements std/Person Contact
  {:name Name :email Email})
ops/renewals.formapalantir
(object-type Renewal
  {:customer (Id std/Organization) ; Account or Customer
   :owner (Id std/Person)
   :amount std/Money})

02–07The preludes

Every platform keeps its own words. They just share a type checker.

A prelude doesn't squeeze Salesforce into someone else's model. It teaches Forma Salesforce's own forms and elaborates them to the Metadata API's own files. Preludes share only Forma's types and the standard library, so a value in one project can refer to a declaration in another.

02The default prelude

@ontology/palantir

Objects, links, actions, and queries: the language the standard library is written in.

runs today · v0.1

The renewal

Your operational model took a year to build and lives inside one vendor's UI. When the contract comes up, the model is the one thing you can't take with you.

The ontology prelude is where Open Ontology started, and it's what @ontology/std is written in. Use it to model your own operations too: object types, link types that carry their own facts, actions that commit as one transaction, and named Datalog queries. It's the same core as Palantir Foundry's Ontology, as a plain file you own, and it elaborates to a portable IR that runs on Triplex.

  • → ontology IR
  • actions → Triplex transactions
  • queries → Datalog
oo add @ontology/palantir
field-service/model.formapalantir
(object-type WorkOrder {:title String :status String})
(object-type Technician {:name String})

(link-type assigned-to WorkOrder Technician
  {:assigned-at Instant})

(: assign (-> (Id WorkOrder) (Id Technician) (Action Bool)))
(define assign [order tech]
  (do! [_ (update! order {:status "assigned"})
        _ (link! assigned-to order tech {:assigned-at (now)})]
    true))

(query assigned-work
  :from WorkOrder
  :where (= status "assigned")
  :select [title])

The sandbox refresh

Billing launched a new plan. Nobody added it to the Plan picklist, so the flow that depends on it fails in UAT. The only diff tool is a 40,000-line XML retrieve.

Objects, fields, picklists, validation rules, and record-triggered flows. They're checked at line:col and elaborated to the same -meta.xml files the Metadata API deploys. Here the picklist's values aren't typed in. They're the lookup keys from the billing project.

  • object → CustomObject
  • field → CustomField
  • record-flow → Flow
  • validation-rule → ValidationRule
oo add @ontology/salesforce
sales/opportunity.formasalesforce
(import "@acme/billing" :as billing)

(object Opportunity
  (field Plan__c (picklist-of billing/prices :by :lookup-key))
  (field Seats__c (Number :precision 6)))

(validation-rule seats-required Opportunity
  (and (= StageName "Closed Won") (blank? Seats__c))
  "Closed deals need a seat count.")

(record-flow mark-customer Opportunity
  :when (= StageName "Closed Won")
  (update! Account {:Type "Customer"}))

@ontology/stripe

Your price book is a program. Write it like one.

preview

The pricing launch

New pricing ships from a spreadsheet. Someone clicks through the dashboard creating fourteen prices and mistypes one tier. The first overage invoice is off by 100×.

Products, prices, tiers, and meters elaborate to the exact Stripe API requests that would create them. Tier order, currencies, and meter references are checked first. The project exports prices as a typed value, so other projects can depend on the price book instead of copying it.

  • product → /v1/products
  • price → /v1/prices
  • meter → /v1/billing/meters
oo add @ontology/stripe
billing/pricing.formastripe
(export prices)

(product pro "Pro")

(price pro-monthly pro
  :lookup-key "pro_monthly" :currency :usd
  :recurring :month :unit-amount 2900)

(meter api-requests :event "api_request" :aggregate :sum)

(price pro-overage pro
  :lookup-key "pro_overage" :currency :usd
  :metered api-requests :tiers [[10000 0] [:inf 20]])

(define prices [pro-monthly pro-overage])

08How a prelude works

A prelude is a Forma file. Elaboration is a typed function.

Since Forma 0.4, a form declares its syntax, its typed holes, its checks, and the IR it produces, all in one definition. Declarations become types that other projects can import. Follow one Stripe price from the prelude that defines it to the Salesforce project that depends on it.

01 · The prelude defines

The pattern sets the syntax and :types sets the holes. (Declares Price) makes each price a declaration that other files can refer to. The body is pure Forma that builds Stripe's request. Nothing in it can reach the network or the disk.

@ontology/stripe/src/prices.formaprelude
(export price Price PriceParams)

(form (price name product {:keys [lookup-key currency
                                  unit-amount recurring
                                  metered tiers]})
  "A Stripe price."
  :types {:name (Declares Price)
          :product (Refers Product)
          :lookup-key String
          :currency Currency
          :metered (Option (Refers Meter))
          :tiers (Option (List Tier))}
  :check stripe/check-tiers
  :ir PriceParams
  (stripe/price-params name product lookup-key …))
02 · You write

Stripe's words, in a file you can diff and review. An unknown option, a missing currency, or a tier out of order is an error at line:col.

billing/pricing.formasource
(price pro-monthly pro
  :lookup-key "pro_monthly" :currency :usd
  :recurring :month :unit-amount 2900)
03 · It elaborates to

Stripe's native request, with a source span on every value. Nothing gets squeezed into a shared model on the way. A reconciler such as Schematics can plan it against the live account.

oo elaborate @acme/billing --jsonPriceParams
{ "kind": "stripe/price", "name": "pro-monthly",
  "span": "billing/pricing.forma:3:1",
  "request": { "method": "POST", "path": "/v1/prices",
    "body": { "lookup_key": "pro_monthly", "product": "pro",
              "currency": "usd", "unit_amount": 2900,
              "recurring": { "interval": "month" } } } }
04 · Other projects see

The billing project's exports are a typed interface. To the sales project, billing/prices is a list of Price declarations, and picklist-of turns their lookup keys into the picklist's value type.

oo interface @acme/billingexports
(: prices (List stripe/Price))
;; pro-monthly  :lookup-key "pro_monthly"
;; pro-overage  :lookup-key "pro_overage"

;; in @acme/sales, Plan__c gets the type
;; (Union "pro_monthly" "pro_overage")

A rename in Salesforce is an error in Okta, before deploy.

Each project is a package with its own prelude, and projects import each other like modules. oo check elaborates the whole graph at once. A break in one platform's config is reported where another platform's config depends on it, before either one is deployed.

10The package manager

Preludes and projects are both packages.

A prelude package publishes a platform's language. A project package publishes your config for that platform, along with its typed exports. The standard library is a package as well. All of them get versions, a lockfile, and a registry entry, and anyone can post a prelude.

sales/ontology.jsonmanifest
{ "name": "@acme/sales",
  "version": "0.3.1",
  "prelude": "@ontology/salesforce@^0.1",
  "std": "@ontology/std@^0.1",
  "entry": "src/",
  "dependencies": {
    "@acme/billing": "^0.1"
  } }
oo add
Install a prelude or a project and pin it in oo.lock with a content hash.
oo check
Elaborate the whole project graph. Errors at file:line:col, plus --json.
oo elaborate
Print a project's native config: metadata files, API requests, or ontology IR.
oo plan
Diff the elaborated config against the live platform through a reconciler.
oo publish
Check, pack, and add a prelude or project to the registry index.

12Status

What exists today, and what is designed.

Your config is the part that carries forward. Here's exactly which parts exist.

Runs today · v0.1

  • The Palantir-style ontology prelude, in Forma or TypeScript, compiled to one JSON IR
  • Located errors, naming rules, and lint with pnpm model:check
  • Actions as atomic, attributed, idempotent Triplex transactions
  • Named Datalog queries with joins, negation, aggregates, and ordering
  • Local in-memory runtime, with field-service and support-desk examples

Preview · v0.2 design

  • The salesforce, stripe, okta, github, and pagerduty preludes. Their syntax will change
  • @ontology/std, implements, cross-project imports, and type checking
  • The oo CLI, manifests, lockfile, and registry
  • oo plan against live platforms, persistence, and an npm release

Ground rules

  1. Preludes are pure Forma, with no install scripts
  2. Platform types implement the standard library; they don't replace it
  3. Each prelude elaborates to its platform's native config
  4. Every reference between projects is typed and checked before deploy
  5. Every elaborated value records its source span

Palantir, Foundry, Salesforce, Stripe, Okta, GitHub, and PagerDuty are trademarks of their owners. Preludes are community-built and modeled on public APIs. Open Ontology isn't affiliated with or endorsed by any of them.
